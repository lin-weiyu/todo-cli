# 项目方向与两周阶段目标

> 当前决策记录：2026-11-20。供学习者和后续接手的项目导师使用。
> 这是**目标和建议**，不是已实现功能清单；实际进度每次以代码、测试和用户反馈重新确认。
> 面试约在 2026-12-04，具体日期、岗位、每天可投入时间尚未确认；以下以每天约 3–4 小时作排期假设，不是完工保证。
> 本页是**当前计划的唯一来源**。[qa-log.md](../qa-log.md) 的 [009] 等条目是历史讨论，可能描述本次决定之前的计划；不要把历史阶段目标与本页合并成两套承诺。

## 1. 长期产品方向

从现有 C++ 个人 Todo CLI 逐步成长为**带文档的个人事务管理系统，再演进为多人项目协作系统**：

1. 个人任务：创建、查询、修改、完成、删除；失败可解释，数据不会无声丢失。
2. SQLite 持久化：数据库管理任务及附件元数据；考虑从原有 JSON 数据导入、异常和备份恢复。数据库事务只保护数据库内的写入，不等于自动完成用户授权或附件文件的备份。
3. 个人任务文档：一项任务可关联多份 PDF、Word、Excel 等文件，支持添加、列出、取回、解除关联；最初不解析或协同编辑文档内容。
4. 多人在线：多个用户从不同客户端通过**服务端**访问数据；服务端识别身份、执行授权、处理冲突与持久化。共享一个 SQLite 文件或让客户端自报用户名，不等于完成在线协作或可信认证。
5. 团队/项目：用户可拥有个人空间并加入多个团队空间；团队空间内有成员、项目和共享任务，后续将附件共享纳入相同权限规则。项目先有“目标说明”，确有跨项目汇总需求时再引入独立的目标层级。

“像 QQ 群”仅借用**成员与共享空间**概念；聊天、在线状态、即时推送、在线文档协同编辑不是当前承诺。任务注意事项可先用文本字段表示；可勾选的完成步骤、多人分工、文件版本和项目进度统计列为后续深化需求，是否实现由后续验收条件决定。

## 2. 目前确实有什么（2026-11-20 的基线，不保证永远最新）

- CLI 支持 `add/list/done/delete/search/edit`，`TodoManager` 用 `IStorage` 的 `load()/save(all)` 整量快照操作，`Storage` 保存 JSON。
- 有 CMake、GoogleTest、GitHub Actions workflow 和 Dockerfile；本次仅验证本地 `cmake --build build` 与 CTest 8/8 通过，未验证远端 CI 或 Docker 新构建。
- `Storage::save()` 目前未检查文件打开与写入失败，`main()` 处理完成后统一返回 0；默认 `data/tasks.json` 是相对于当前运行目录的路径，`TODO_DATA_FILE` 可覆盖。业务类还负责终端打印。缺少 CLI 端到端、坏数据和关键失败路径测试。
- [当前业务与存储接口](../../include/core/TodoManager.h)、[存储接口](../../include/storage/IStorage.h)、[存储实现](../../src/storage/Storage.cpp)、[CLI](../../src/cli/CommandHandler.cpp)、[已有测试](../../tests/TodoManagerTest.cpp)。

这些是学习机会，**不是** SQLite、附件、多人服务已经落地的证明。旧问答里的“路径问题已彻底解决”仅针对其当时验证的运行方式；默认路径仍依赖运行目录。已有 CI workflow 也不代表仓库已启用阻止失败合并的规则。

## 3. 两周内的推荐交付：真实完成的个人版 + 协作设计

这是近期面试的**阶段目标**，不是长期产品愿景的缩写，也不代表自动承诺实现所有条目。优先级按依赖与价值决定，而非按工具热度。

### P0 — 可靠的现有 CLI 与 SQLite 持久化（优先完成）

- 给任务操作定义成功与失败契约；保存失败不能提示成功，错误返回非零退出码，损坏数据不能被当成空数据覆盖。
- 设计任务表及约束，按任务操作读写，而不是把 `IStorage::load()/save(all)` 的全量快照原封不动套在数据库上。
- 学习 SQLite 的参数绑定、事务与 C++ RAII 资源管理；测试正常持久化、跨进程重启、无效输入、保存失败。
- 旧 JSON 不能默默丢掉：设计有验收测试的一次性迁移/导入，保留源文件，坏数据时失败且不留下半份导入结果。（2026-11-25 用户决定本期跳过：现有 `data/tasks.json` 仅 2 条测试数据、迁移价值低，后续需要再补；详见 qa-log [015]。当前 JSON 数据仍留在 `data/tasks.json`，切到 SQLite 后不自动出现。）
- 数据“保护”还需要明确数据文件位置、备份与恢复验证、出错时保留数据；SQLite 不是自动完成这些工作的安全保险箱。

### P1 — 多文档个人任务（推荐作为面试演示的重点功能）

- 一项任务可关联多份真实文档；先做“添加、列出、取回、解除关联”这条完整最小流程，不扩展成 PDF/Office 阅读器、协同编辑器。
- 推荐**受应用管理的本地附件目录 + SQLite 中的附件元数据与任务关联**；原始文件名用于展示，物理文件由应用生成内部标识，避免只记录用户电脑上的绝对路径（换设备就不可用）。外部 URL 链接是另一个可选需求，不和上传文件混成同一机制。
- 明确文件大小/类型限制、任务删除时的附件处置；设计文件操作成功而数据库操作失败、或相反时的清理/恢复规则。数据库事务**不**自动覆盖文件系统动作。个人版先管理本人可访问的数据；日后团队版必须重新审视下载权限。
- 附件内容与 SQLite 文件要一起考虑备份和恢复，不能只备份数据库就宣称资料受保护。

### P2 — 为团队协作建立可验证的设计边界（本期设计与测试，不冒充已上线）

- 先确定用户、个人空间、团队空间、成员关系、项目、任务、附件之间的归属；一个用户可加入多个团队。
- 先定最小权限规则：成员能访问自己所属空间中的内容，非成员不能访问；未来角色可从 owner/admin/member 起步，不必一次设计复杂权限矩阵。
- 对模型和权限规则写小规模测试/设计说明；**如果尚无网络服务和可信身份认证，只能叫协作领域与权限原型，不能说“两人同时在线处理”。**

### 为什么不把所有长期目标压进两周

真正的多人在线还需要服务端 API、可信身份认证、授权、并发冲突策略、部署与网络测试；团队文档共享还要下载权限、文件生命周期与版本。按初学者每天约 3–4 小时估计，两周同时完成 SQLite、真实附件、认证、团队在线与可靠交付不现实。若面试岗位要求服务端在线演示，导师应**明确与用户讨论**是否把附件后移并把有限时间投入最小 API，不可私下删掉用户已认可的目标。

## 4. 后续里程碑：真实多人协作

### 第一阶段：最小在线协作

- 单个服务端统一处理客户端请求；有可验证的用户身份及登录/会话机制，不能仅根据请求传来的 `user_id` 信任身份。
- 团队可有多个成员，用户可加入多个团队；团队里有项目与共享任务。读取、更新、删除均做服务端权限校验（含附件下载）；禁止跨组越权。
- 能从两个独立客户端发请求：各自可处理有权限的任务，非成员访问被拒绝。多线程/多请求时不共享不安全的数据库连接用法，保持事务短且处理忙碌状态。
- SQLite WAL 能支持读写并行，但同一数据库同时只能有一个写事务；不宣称无限写并发，也不在网络共享盘上直接开放数据库文件。

### 第二阶段：协作质量与增强

- 任务/附件修改冲突：先检测旧版本并提示重试或保留文件历史，避免后写入者无声覆盖前者；这与数据库层写事务串行是不同的问题。
- 完成步骤 checklist、任务注意事项/操作记录、多个项目目标统计、附件版本与恢复；只在需求明确后增加实时通知或聊天。
- 有测量结果证明瓶颈时再评估替换数据库；不要为了显得“大型项目”提前上微服务、消息队列或缓存集群。

## 5. 两周排期建议与关口

> D1 是开始实施的相对时间，不代表 2026-11-20 起项目已经开始执行。实际启动日期、工时与目标岗位由用户确认后再细化；不将未来日期写成历史完成记录。

| 阶段 | 要解决的问题 | 可展示的证据 |
|------|--------------|--------------|
| D1–D2 | 写下个人任务与文档的验收条件；复现保存失败等旧行为 | 需求清单与先红后绿的测试案例 |
| D3–D5 | SQLite 最小任务读写、旧 JSON 导入与异常处理 | 重启后仍有数据，失败不覆盖旧数据 |
| D6 检查点 | 评估真实进度、剩余工时与风险 | 共同决定是否调整附件范围，**不擅自宣布删掉** |
| D7–D10 | 一个任务关联多文档及其取回/删除，隔离测试数据 | 可从独立进程演示文件与任务的关系 |
| D11–D12 | 协作模型/权限规则的设计及必要测试；整理构建、运行、备份说明 | 清晰区分“设计/原型”和“已上线能力” |
| D13–D14 | 冻结范围、面试演示与模拟追问 | 5 分钟讲清问题、取舍、实现、验证、局限 |

若实际进度不及预期，优先保证已实现的个人任务与 SQLite 数据完整、测试与文档可信，明确向用户说明哪些附件或协作内容尚未落地，再共同调整时间安排；不能把愿景包装成成品。面试准备还包括 C++、数据结构、操作系统等岗位基础，项目实践不能取代它们。

## 6. 导师如何陪用户实施

- 把用户当作第一次做工程项目的学习者：先给结论、解释为什么推荐这个方案，简述替代方案代价，再用小步骤引导用户自己实现核心代码。
- 一次只解决一个可验收的真实问题，遵循**需求 → 设计 → 测试 → 实现 → 验证 → 回顾**；解释何为完成（Definition of Done）：正常与失败路径有验证、必要文档已更新、本人能讲清取舍。
- 工具按需学：现有 Git、CMake、GoogleTest/CTest、GitHub Actions、Docker、Debug ASan；必要时再逐步加入工具，不以工具数量衡量项目质量。CMake Presets 若要增加，先核对 schema 与项目最低版本 3.14 是否兼容。
- 每次答疑之后按 [qa-log.md](../qa-log.md) 模板追加问答和目录索引，出现新工程概念时补充 `docs/topics/`；**用户明确要求讨论且不修改时不要写文件**。面向后续接手者：历史讨论不覆盖本页的最新目标。
- 不使用个人 `data/tasks.json` 或真实私人文档作实验数据；使用隔离的临时数据。已有未提交修改先检查并保留。做完只汇报实际完成与实际验证，不虚构 CI、Docker、并发或安全结论。

## 7. 第一课的建议切入点

先带用户理解 [Storage.cpp](../../src/storage/Storage.cpp) 为什么可能保存失败却没有显式报告，再讨论错误怎样传至业务层和 CLI、怎样写失败测试；随后再进入 SQLite 与多文档任务。不应因此忽视用户对长期多人协作产品的明确愿景。
