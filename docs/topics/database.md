# 数据库：从 JSON 文件到 SQLite，再到多人协作数据库

> 主题：Database / SQL / SQLite / PostgreSQL / 数据建模 / 事务 / 附件元数据

## 1. 为什么 JSON 文件不够用了

当前项目用 JSON 文件保存任务，本质是「一次把所有任务读进内存，修改后再把全量快照写回文件」。它适合入门，但随着功能变多会暴露问题：

- **查询能力弱**：例如按状态、关键词、截止日期、团队、项目组合查询，需要自己遍历和过滤。
- **约束弱**：无法自然表达「任务必须有标题」「附件必须属于某个任务」「团队任务必须属于某个团队」。
- **局部更新困难**：修改一条任务也常常要重写整个文件。
- **失败处理复杂**：写到一半失败、坏 JSON、并发运行两个程序，都容易造成覆盖或丢数据。
- **扩展关系困难**：任务、附件、用户、团队、项目之间是多张表/多种关系，不适合继续塞进一个大 JSON。

数据库解决的核心不是「换个文件格式」，而是提供：结构化数据、查询语言、约束、事务、索引和并发控制。

## 2. 常见数据库类型

### 2.1 关系型数据库（Relational Database / SQL）

代表：SQLite、PostgreSQL、MySQL/MariaDB。

特点：数据放在表里，通过主键、外键和 SQL 查询组织关系。适合任务、附件、用户、团队、权限这类「关系明确」的数据。

优点：

- 数据关系清楚，适合建模；
- 支持事务，能保证一组修改要么一起成功、要么一起失败；
- 支持约束和索引，数据更可靠、查询更快；
- SQL 是通用技能，面试和实际工程都常见。

缺点：

- 需要先设计表结构；
- 修改表结构要做迁移；
- 初学时要理解 SQL、事务、连接、错误处理。

### 2.2 文档数据库（Document Database）

代表：MongoDB、CouchDB。

特点：保存类似 JSON 的文档。适合字段经常变化、每条记录结构不固定的数据。

优点：

- 和 JSON 心智模型接近；
- 灵活，新增字段方便。

缺点：

- 任务、附件、用户、团队、权限之间关系强时，反而容易把关系处理推回应用层；
- 对初学者来说，容易绕开数据建模训练；
- 本项目不需要一开始用它。

### 2.3 键值数据库 / 缓存

代表：Redis、RocksDB、LevelDB。

特点：按 key 取 value，非常快。Redis 常作缓存、排行榜、临时会话；RocksDB/LevelDB 常嵌入到系统内部。

优点：

- 简单、快；
- 适合缓存、计数、临时状态。

缺点：

- 不适合表达复杂关系；
- 不是本项目主数据存储的首选。

### 2.4 搜索引擎

代表：Elasticsearch、OpenSearch、Meilisearch。

特点：擅长全文搜索、模糊搜索、复杂排序。

优点：

- 搜索能力强。

缺点：

- 通常作为关系型数据库旁边的搜索系统，不作为任务/权限的唯一真相源；
- 运维复杂，不适合当前阶段。

### 2.5 对象存储 / 文件存储

代表：本地附件目录、S3、MinIO。

特点：保存真实文件内容，如 PDF、Word、Excel、图片。

优点：

- 适合保存大文件；
- 可与数据库配合：文件内容在对象存储，元数据在数据库。

缺点：

- 不是数据库查询系统；
- 文件写入和数据库写入之间要设计一致性与恢复策略。

## 3. 本项目推荐路线

### 第一阶段：SQLite

推荐先用 SQLite。SQLite 是嵌入式、无服务端、零配置的 SQL 数据库；程序直接打开一个 `.db` 文件读写。它非常适合当前 C++ CLI 项目。

为什么适合：

- **部署简单**：不像 PostgreSQL/MySQL 那样要先启动数据库服务；一个本地文件就能跑。
- **学习价值高**：能学 SQL、表设计、主键、外键、索引、事务、参数绑定、迁移。
- **和当前项目阶段匹配**：现在还是个人 CLI，不需要多人在线数据库服务。
- **便于面试讲述**：可以清楚讲出从 JSON 快照到数据库表、事务和约束的工程升级。

要注意：

- 不要只把 `load()/save(all)` 换成读写 SQLite；那只是把 JSON 快照换成数据库快照，数据库优势没有发挥出来。
- 应逐步改成按操作访问：`addTodo` 插入一行、`markDone` 更新一行、`deleteTodo` 删除一行、`list/search` 查询。
- 每次业务操作要有清楚事务边界。
- 旧 JSON 数据要设计一次性导入，不能默默丢弃。

### 后续多人在线：PostgreSQL

当项目进入「多个用户通过客户端访问同一个服务端」阶段，推荐引入 PostgreSQL。它是服务端关系型数据库，适合 Web/API 服务统一连接、认证授权、团队协作和更复杂的并发访问。

为什么不是一开始就上 PostgreSQL：

- 需要安装、启动和管理数据库服务；
- CLI 学习阶段会被连接配置、账户、端口、服务管理分散注意力；
- 当前还没有服务端和多人在线访问，提前上会增加复杂度。

为什么未来要考虑 PostgreSQL：

- 多客户端在线协作更符合客户端/服务端数据库模型；
- 用户、团队、项目、权限、附件元数据都适合关系型建模；
- 并发访问、备份、权限、运维能力更适合长期产品。

## 4. 附件文件怎么存

推荐：**文件内容放在应用管理的附件目录或对象存储，数据库保存元数据和关联关系**。

示例元数据字段：

- `id`：附件内部 ID；
- `task_id`：属于哪个任务；
- `original_name`：用户看到的原文件名；
- `stored_name` / `object_key`：应用内部保存名；
- `mime_type`：文件类型；
- `size_bytes`：文件大小；
- `sha256`：校验值；
- `created_at`：添加时间。

不推荐第一阶段直接把 PDF/Word/Excel 的完整二进制都塞进数据库作为主方案。数据库很适合保存关系和元数据，但真实文件还要考虑大小、复制、备份、下载权限和恢复。

## 5. 下一步学习顺序

1. 先画数据模型：`todos` 表最小字段，未来 `attachments` 表如何关联。
2. 学最小 SQL：`CREATE TABLE`、`INSERT`、`SELECT`、`UPDATE`、`DELETE`。
3. 学 SQLite C API/封装：打开数据库、准备语句、绑定参数、执行、读取结果、释放资源。
4. 用 RAII 包装数据库连接和语句，避免忘记关闭。
5. 用测试驱动实现：先让 `add/list` 使用 SQLite 跑通，再扩展 `done/delete/search/edit`。
6. 设计 JSON 导入：成功后保留原文件，失败时数据库不留下半份数据。

## 6. 面试表达

可以这样讲：

> 我一开始用 JSON 文件做持久化，优点是简单，但随着任务、附件、用户、团队和权限关系变多，JSON 的查询、约束、事务和局部更新能力不足。所以第一阶段我选择 SQLite：它适合本地 CLI，能学习完整的关系型数据库基础，又不需要部署服务端。等项目进入多人在线协作，我会把数据库放到服务端，优先选择 PostgreSQL；文件内容不直接作为关系数据处理，而是由文件存储保存，数据库保存附件元数据和权限关系。

## 7. 在实际项目中引入数据库的流程

以当前 todo-cli 为例，推荐按下面顺序推进：

### 7.1 先从业务对象推导表

当前业务对象是 `Todo`：

- `id`：任务唯一编号；
- `text`：任务内容；
- `done`：是否完成。

第一张数据库表就是 `todos`：

```sql
CREATE TABLE IF NOT EXISTS todos (
    id INTEGER PRIMARY KEY,
    text TEXT NOT NULL,
    done INTEGER NOT NULL DEFAULT 0
);
```

这一步的重点不是语法，而是映射关系：一个 C++ 对象通常对应数据库里的一行，成员变量通常对应表里的列。

### 7.2 再确定第一版接入边界

当前项目已有 `IStorage::load()/save(all)`，它是全量快照接口。第一版可以新增 `SQLiteStorage` 实现这个接口：

- `load()` 执行 `SELECT id, text, done FROM todos ORDER BY id;`；
- `save(todos)` 在一个事务里清空旧数据，再把传入的完整任务列表插入表中。

这一步的好处是改动小，能先学会 SQLite 和测试；缺点是仍然保留快照思维。因此它只是迁移桥梁，不是最终架构。

### 7.3 数据库代码的基本生命周期

SQLite 在 C/C++ 中通常按这个顺序使用：

1. `sqlite3_open`：打开数据库文件；
2. `sqlite3_exec`：执行简单 SQL，例如建表、开启事务；
3. `sqlite3_prepare_v2`：把带参数的 SQL 编译成语句；
4. `sqlite3_bind_*`：绑定参数，避免字符串拼接 SQL；
5. `sqlite3_step`：执行语句或读取一行结果；
6. `sqlite3_finalize`：释放语句；
7. `sqlite3_close`：关闭数据库连接。

C++ 里应把连接和语句封装成 RAII 类，让析构函数自动关闭和释放资源。

### 7.4 测试先行

第一版 SQLite 存储至少需要这些测试：

- 空数据库读取返回空列表；
- 保存两条任务后能重新读取；
- `done` 状态能保存和读取；
- 保存空列表会清空表；
- 用同一个 `.db` 文件重新创建 storage，数据仍然存在。

这些测试证明“数据真的进了数据库”，而不是只存在内存里。

### 7.5 接入构建和运行环境

工程上还要同步更新：

- `CMakeLists.txt`：查找并链接 SQLite；
- CI：安装 `libsqlite3-dev`；
- Dockerfile：安装 `libsqlite3-dev`；
- CLI 默认路径：从 `data/tasks.json` 调整为 SQLite 数据库文件，例如 `data/tasks.db`，并考虑保留环境变量覆盖。

### 7.6 第二阶段再做真正数据库化

第一版 `SQLiteStorage` 跑通后，再把接口从快照式改为操作式，例如：

- `addTodo(text)` → `INSERT`；
- `listTodos()` → `SELECT`；
- `markDone(id)` → `UPDATE`；
- `deleteTodo(id)` → `DELETE`；
- `searchTodos(keyword)` → `SELECT ... WHERE text LIKE ...`。

这才是真正发挥数据库优势的阶段。
